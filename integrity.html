Three Layers of Integrity

A common misconception in secure data pipelines is that a single hash solves all problems. It doesn’t. To prove a file is authentic, you need to separate the logical content from the physical artifact.

What SPCMP is for. SPCMP gives a float32 dataset one canonical, reversible form with a built-in commitment to its content. Same data, same container. Altered data, failed verification.

The Layers

Each demo below is an illustration of behaviour we measured. Try the attacks.

LAYER 1

Logical-Content Integrity

SPCMP’s content commitment, built on SHA-256 Merkle hashing, detects any alteration of the decoded data: the float32 values and their original order.

If the decoded content is identical, the commitment passes. A change that touches only the compression layer, and leaves the data byte-for-byte the same, is not a change to the data.

Limit: the commitment travels inside the file. Someone who can rewrite the file can recompute it. Layer 1 catches corruption and edits that leave the commitment alone. It does not say who made the file.

LAYER 2

Artifact Integrity & Authenticity

If your threat model requires the exact serialized bytes to be unchanged, or you need to know who produced the file, sign the physical artifact.

The producer’s signing accessory takes a SHA-256 hash of the finished .pcmp file and signs it with Ed25519 into a detached manifest. The combined verifier checks the signature, the pinned key and the exact file hash before it parses the file at all, then runs the Layer 1 content check.

The private key stays with whoever is asserting provenance, protected by a passphrase or an HSM. Samayuktam never holds it.

Detached: the signature lives in a separate manifest, so the .pcmp file itself is unchanged.

LAYER 3 · EXTERNAL

Execution Attestation

A signed, verified file establishes what the data is and who produced it. It does not establish how it was generated.

Proving that a specific script ran on a specific machine requires hardware attestation or execution logs. Those sit outside the SPCMP protocol.

Best fit: Core Verification

Clients who generate and verify SPCMP artifacts inside their own trusted environment, and need logical-integrity verification without adding a signing workflow.

Best fit: Authenticated Verification

Clients who move artifacts across trust boundaries or need provenance, auditability and exact-byte integrity: cloud pipelines, AI artifact distribution, scientific data workflows.

The signing key belongs to the client, who is the one asserting the provenance of its own artifact. Samayuktam does not distribute its private signing key. Authenticated Verification does not replace Core Verification. It adds an authentication layer around the same core artifact, and a valid signature does not prove a computation was honest, which is why the content check still runs afterward.

Assumptions: Layer 1 binds both the values and their original order. Layer 2 signs a manifest that contains the exact file digest. The verifier pins the signing key independently, not from the file it is checking.

Cryptographic commitments establish the integrity of the data they cover. Signatures bind an artifact to a signing key and an authenticated statement about it. Neither establishes that the computation was correct or that the signer was authorised for this specific operation. A validly signed artifact can faithfully preserve an incorrect model output.

The Deployment Path

Start where an artifact changes hands, not inside every live transaction. The example below is a bank moving a risk-model artifact between environments. Illustrative, not a statement of any customer’s setup.

STEP 1

Data and computation

Bank data, model, code and execution environment.

STEP 2

Canonicalize and commit

SPCMP puts the data into its canonical form and computes the content commitment.

STEP 3

Finish the artifact

The .pcmp file is finalized. Only now is it hashed, so the signature never has to cover a file that contains its own hash.

STEP 4

Authenticate the exact file

A signing service backed by an HSM or key-management service signs the file’s SHA-256 digest. The private key never leaves it.

STEP 5

Distribute file and signed manifest

The manifest binds the digest to the profile and version, file length, content commitment, key ID, and a release identifier that blocks replay of older files.

STEP 6

Independent verification

The bank’s own verifier checks the signature and exact file hash first, then runs the SPCMP content and structure checks.

STEP 7

Accept or quarantine

Accept only if every required check passes. Otherwise reject, quarantine and log. There is no silent fallback to the weaker check.

Controls the receiving organisation still owns

Key custody

Signing keys stay apart from whoever produces the file. The bank pins trusted public keys, defines what each key may sign, and runs rotation and revocation.

Signed manifest

A defined, canonically encoded manifest, so the exact signed bytes are unambiguous.

Replay and rollback

A valid signature does not mean newest. The signed manifest carries a release identifier the verifier checks, so an old file cannot replace a new one.

Audit evidence

Digest, commitment, key ID, verifier version, result, time and release ID go to tamper-evident storage, with duties separated.

Where It Fits

Anywhere a float32 artifact changes hands and someone downstream has to trust it without redoing the work.

These are deployment patterns, not certifications. SPCMP alone does not supply every control a regulated environment requires.
